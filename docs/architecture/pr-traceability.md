# Сопоставление функций Booka и Букраста при изменениях

[Реестр сценариев переноса в Notion](https://app.notion.com/p/970f1eab10e041489e285725a697b513) — отдельная база, где каждая строка соответствует действию пользователя или предметному правилу. Это не список файлов.

## При каждом запросе на объединение

1. Открыть существующую карточку сценария или создать новую в реестре.
2. Заполнить [шаблон PR](../../.github/PULL_REQUEST_TEMPLATE.md): ровно один тип работы, ссылку на карточку, старое и новое поведение, проверки, остаток.
3. Указать ссылки на код и тесты Booka и Rust и текущие различия в самой карточке Notion.
4. Добавить URL запроса на объединение в карточку Notion и обновить сведения о проверках.
5. Не менять статус «Реализовано» без работающего пользовательского пути и тестов; «Сверено» — только после сравнения важных правил, отказов и пограничных случаев.

Для технической работы без пользовательского сценария выбирается «Техническая задача» и ссылка на конкретную задачу Notion, не на главную страницу проекта и не на доску.

## Автоматическая проверка

`.github/workflows/check-scenario-link.yml` запускается при создании, изменении описания и обновлении запроса на объединение.

- Не принимает пустое описание, непомеченный или двойной тип, незаполненные разделы.
- Для пользовательских изменений требует URL конкретной страницы Notion, а не URL всей базы переноса или плана проекта.
- Для технических изменений требует URL конкретной задачи Notion.
- Проверяет **формат** ссылок, не доступ к Notion и не принадлежность страницы нужной базе. Внешний API Notion пока не подключён; это нельзя считать проверкой фактического переноса.
- Не выполняет пользовательское содержимое описания как команду. Отдельные сборочные и архитектурные проверки продолжают действовать.

Локально:

```bash
python -m unittest discover -s tests/architecture -p 'test_pr_scenario_traceability.py' -v
python tools/check_pr_scenario.py --body-file /path/to/pr-description.md
```

## Обязательность для main

После успешной проверки самого правила включить защиту `main`: `Settings → Branches` (или `Settings → Rules → Rulesets`) → требовать PR и успешную проверку **Scenario traceability**. До настройки защиты ошибку будет видно в GitHub Actions, но она не обязательно запретит ручное объединение.

Не назначать проверку обязательной до появления её успешного результата на реальном PR, иначе можно случайно заблокировать ветку. После включения проверьте, что PR без карточки действительно нельзя объединить.

Для существующих незавершённых PR нужно привести описание к новому шаблону. Исключений по умолчанию нет; технический PR получает ссылку на конкретную задачу.
